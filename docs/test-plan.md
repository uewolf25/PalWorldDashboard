# テスト仕様書

管理ツールの品質を確認する手順。**単体テスト（自動）** と **結合テスト（実機・手動）** の2段構え。

- 単体テストは CI と手元で常時回す。ゲームサーバもネットワークも要らない
- 結合テストはリリース前と設定変更後に実機で1周する。**モックでは再現できない領域**（プロセスの寿命・ファイルの所有者・処理にかかる時間・権限）を見る

障害時の調べ方は [運用メモ](operations.md)、設計の意図は [README](../README.md)。

---

## 1. 単体テスト（自動）

### 1.1 実行

```bash
cd /opt/dashboard-Pal/backend
.venv/bin/python -m pytest -q
```

**期待結果: 全件 passed、失敗0。**

```bash
.venv/bin/python -m pytest -q tests/test_restart.py     # 個別に流す
.venv/bin/python -m pytest -q -k preflight              # 名前で絞る
.venv/bin/python -m pytest -q --lf                      # 前回落ちたものだけ
```

秘密情報チェックも同じ扱いで通すこと。コミット時は `.githooks/pre-commit` が、
CI では `.github/workflows/ci.yml` が自動で走らせる。

```bash
cd /opt/dashboard-Pal && python3 scripts/check_secrets.py
```

### 1.2 前提

モック Palworld REST API に ASGI 直結するので、**ポートもネットワークも使わない**。
`conftest.py` の `settings` fixture が `pal_service_backend="simulated"` を強制するため、
ホストに `systemctl` があってもなくても結果は変わらない。

### 1.4 単体テストで**確認できない**こと

ここが結合テストの存在理由。

- ゲームサーバのプロセスが本当に止まる / 起動するか
- `PalWorldSettings.ini` を実際に書き込めるか（所有者・権限・サンドボックス）
- ワールド保存が制限時間内に終わるか
- sudo / polkit / ユニットの存在といった権限まわり
- ゲーム内アナウンスが日本語で正しく出るか
- ブラウザでの実操作

## 2. 結合テスト（実機・手動）

### 2.1 実施条件

- **プレイヤーがいない時間帯に行う。** T-07 以降はサーバを停止する
- 事前に設定ファイルをバックアップしておく（[2.2](#22-事前準備)）
- 別ターミナルでログを流しておく

```bash
journalctl -u dashboard-Pal -f
```

判定は **OK / NG / 対象外** で記録する。NG が出たらそこで止め、[運用メモの切り分け](operations.md#切り分け)へ。

### 2.2 事前準備

```bash
sudo cp /etc/dashboard-Pal.env /etc/dashboard-Pal.env.bak
sudo cp /etc/systemd/system/dashboard-Pal.service /etc/systemd/system/dashboard-Pal.service.bak
sudo -u mntuser git -C /opt/dashboard-Pal log --oneline -1     # 試験対象の版を控える
```

### 2.3 テスト項目

順序は**壊れたときの被害が小さい順**。上から順に実施する。
